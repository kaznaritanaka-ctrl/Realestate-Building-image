# 写真品質の画像生成：方式とデータ送受信（検討）

- 状態：検討ドラフト（2026-11-05）。親Issue #1 / 関連 #6
- 前提：形と規模はエンジン（決定的）が決め、AIは外観の仕上げだけを担当する。3D（three.js）で表示している形を「正」とする

## 1. 方式の比較

| 方式 | 形の再現性 | 品質 | 1件あたり費用 | 運用の手間 | 備考 |
|---|---|---|---|---|---|
| A. 自宅PC：Blender＋ComfyUI | ◎（深度・輪郭で拘束） | ○〜◎ | 電気代のみ | 大（PC常時稼働・AMD環境） | 現行案。1枚2〜3分 |
| **B. 自宅PC：ComfyUIのみ（制御画像はブラウザで作成）** | ◎ | ○〜◎ | 電気代のみ | 中 | Blender工程を省く。推奨の出発点 |
| C. OpenAI画像API（下絵からの編集） | △〜○（階数・窓が変わる恐れ） | ◎ | 中品質で約$0.04/枚 | 小（自宅PC不要） | 品質比較はDotsで実施中 |
| D. サーバーレスGPUでComfyUI（RunPod等） | ◎ | ○〜◎ | 数円/枚程度（要見積もり） | 小 | Bのワークフローをそのまま移せる。規模拡大時の本命 |

**結論（案）**：
1. まず **B** で作る（PoC〜小規模公開）。制御画像は three.js で作るので、ブラウザの3Dと仕上げ画像の形が一致する
2. **C** は品質比較と、自宅PCが止まっているときの代替に使えるよう、生成部分を差し替え可能にしておく
3. 件数が増えたら、同じComfyUIワークフローを **D** に移す（自宅PCの常時稼働から解放される）
4. Blender（A）は、陰影・素材を作り込んだ下絵が品質上どうしても必要だと分かった場合だけ追加する

## 2. 制御パッケージ（ブラウザで作り、R2に保存）

「3案を作る」で送信した時点で、ブラウザが案ごと・視点ごとに次を書き出す（Blender不要、表示と同じ描画処理）。

| ファイル | 内容 | 用途 |
|---|---|---|
| `base.png` | 白模型（影・周辺建物つき） | img2img の下絵／OpenAIへの入力 |
| `depth.png` | 深度（近いほど白） | ControlNet Depth |
| `lineart.png` | 輪郭線（エッジ） | ControlNet Lineart/Canny |
| `mask.png` | 計画建物だけ白 | 仕上げ範囲の限定・品質チェック |
| `spec.json` | 用途・規模・階数・屋根・カメラ・周辺の有無・エンジン版 | プロンプト組み立て・再現 |

- 視点は2つ（道路側の正面斜め・俯瞰）× 3案 → 6組。1組あたり合計約0.5〜1MB
- 利用者のアップロード画像は扱わない（入力は全部こちらで生成したもの）→ 安全性と権利の問題を避ける
- glTF（3Dデータ）も同時に保存し、将来Blenderを使う場合の入力にする

## 3. データの流れ（自宅PCは外向き通信だけ）

```
ブラウザ ──(1) POST /api/jobs：制御パッケージ＋メール＋同意──▶ Worker ──▶ D1(jobs) / R2(inputs)
                                                                        │
自宅PC runner ──(2) POST /api/runner/lease（10秒ごと）──────────────────┘
   │  ◀── ジョブ情報＋入力ファイルのURL
   ├─(3) GET 入力ファイル（Worker経由でR2から）
   ├─(4) ComfyUI（127.0.0.1:8188）に固定ワークフローを投入 → 生成 → 品質チェック
   ├─(5) PUT 出力画像（Worker経由でR2へ）
   └─(6) POST /complete（失敗時 /fail）──▶ Worker：完了メール送信・結果ページ公開
```

- **pull型**：自宅PCは受信ポートを開けない。Cloudflare Tunnel等の受け口も作らない
- **lease**：取得から10分で期限切れ。heartbeatが止まれば別の回で再取得。再試行は2回まで
- 認証：runner専用トークン（Workerのシークレット）。他の用途と共有しない
- 転送はWorker経由（R2バインディング）で行い、R2のS3キーを自宅PCに置かない
- 通信量：待機中は10秒ごとの問い合わせで1日約8,600回。Workersの無料枠（1日10万回）に収まる

### runner の役割（Python、Windowsの専用ユーザーで実行）
1. lease を取る → 入力を一時フォルダに保存
2. `spec.json` からプロンプトを組み立てる（用途・外観テイスト・屋根・階数。自由入力は使わない）
3. ComfyUI API にワークフロー（JSON）を投入：SDXL系＋ControlNet（Depth＋Lineart）、マスクで建物部分だけを仕上げる
4. **品質チェック**：生成画像から深度を推定し（Depth Anything 等のノード）、マスク内で入力深度との相関を見る。基準未満なら seed を変えて再生成
5. 出力をアップロード → complete
6. ComfyUI は 127.0.0.1 のみで待ち受け。カスタムノードは固定・更新は手動

## 4. 決めること・確認すること

| 項目 | 推奨 | 確認 |
|---|---|---|
| 生成モデル | SDXL系＋ControlNet（Depth/Lineart） | **モデル・LoRA・ControlNetの商用利用ライセンス**（Flux dev 等は商用に制限あり） |
| AMD Radeon RX 6700 XT（Windows）での実行方式 | 現在動いている構成を維持 | ROCm/ZLUDA/DirectML のどれか、VRAM 12GBでSDXL＋ControlNet 2本が回るか |
| 1件の枚数 | 3案×2視点＝6枚（または正面のみ3枚） | 処理時間（2〜3分/枚なら6枚で15分前後） |
| OpenAI APIの併用 | 比較用に生成部分を差し替え可能にしておく | 従量課金の承認、Dotsでの比較結果 |
| サーバーレスGPUへの移行条件 | 月の生成件数・自宅PCの停止頻度で判断 | 見積もり（RunPod / ComfyDeploy / fal 等） |

## 5. 実装順（案）
1. ブラウザで制御パッケージ（base/depth/lineart/mask/spec）を書き出す機能 → 手元でダウンロードしてComfyUIで手動検証
2. ComfyUIワークフローを固める（Museの自宅PCで）
3. Worker：jobs API・runner API・R2保存・完了メール
4. runner（Python）
5. 品質チェックと再生成
